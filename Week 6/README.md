# Week 6 — Dev Assistant (Day 31 / Task 1)

Десктоп-ассистент разработчика: RAG по документации проекта + живой git-контекст (MCP-тулы).

База — код Week 4 (RAG-движок, чанкеры, Ollama `bge-m3`, SQLite). Вместо wiki-статей — проекты.

## Запуск

```sh
cd "Week 6"
./kotlin run --module desktop
```

Нужны: запущенная Ollama (`ollama serve` + `ollama pull bge-m3` для эмбеддингов
и, например, `ollama pull qwen3:32b` для локальной LLM) и — только для облачного
режима — `DEEPSEEK_API_KEY` (env, корневой `.env` или `~/.ai-advent-week6/.env`).

Данные: `~/.ai-advent-week6/` — `rag.db`, `projects.json`, `chats.json`, `repos/` (клоны).

## Проекты

- `+` в панели «Проекты»: имя + git-URL (клонируется в `repos/<имя>`) или локальный путь (на месте).
- Клик — выбрать проект для вопросов. `⟳` — обновить (`git pull` + доиндексация), `×` — убрать.
- Индексируется только документация: `README*`, `docs/**` (целиком, включая примеры), `*.md`, схемы API (`openapi*.yaml/json`), `*.sql`/`graphql`. Код проекта (`.kt/.java/.py/.js/.ts` вне `docs/`) НЕ эмбеддится.
- Внизу левого сайдбара — «⚙ Настройки»: выбор LLM (локальная Ollama / DeepSeek-облако) и эмбеддинг-модели, как в мобильном Week 5. Пресеты для M3 Pro 64 ГБ: `qwen3:32b` (баланс), `qwen2.5-coder:32b` (код), `llama3.3:70b` (максимум), `qwen2.5:7b` (быстрая).

## Команды чата (Task 1)

- `/help [вопрос]` — без аргумента справка, с вопросом — ответ по проекту (RAG + ветка).
- `/branch` — текущая ветка/коммит (MCP-тул `GitTools`, без LLM).
- `/files [фильтр]` — список файлов проекта (`git ls-files`, без LLM).
- `/diff` — изменения рабочего дерева (`status` + `diff --stat`, без LLM).
- `/status` — проект, путь, ветка, файлы в индексе.
- `/projects` — список проектов.
- Обычный текст — RAG-ответ со ссылками `[N]` и раскрывашкой «источники».

## Как закрыт Task 1

- RAG: README + `docs` + схемы API в SQLite-векторах, чанки `fixed`/`structure`.
- MCP: `core/src/project/GitTools.kt` — `branch` (минимум), `listFiles` (`/files`), `diffStat` (`/diff`), `readFile`, `commit`; ветка/коммит подмешиваются в системный промпт.
- `/help` отвечает на вопросы о структуре проекта с цитатами файлов.

## Task 2 — AI-ревью PR (День 32)

- `cli review --base origin/main --head HEAD --format json --out review.json`:
  freshness RAG (`indexedCommit` vs HEAD + `staleSources`) -> PR-diff (`merge-base...head`) ->
  поиск правил по каждому файлу -> LLM JSON -> валидация строк.
- Ключ только из env `DEEPSEEK_API_KEY` (в Action — из `secrets.DEEPSEEK_API_KEY`), на диск/VPS не пишется.
- Вывод — `ReviewResult` (`core/src/rag/Review.kt`): `summary` (баги/архитектура/рекомендации) + `comments[{path,line,severity,body}]` — только `+`-строки diff, иначе GitHub вернёт 422.
- `--dry-run` — без LLM: freshness + статистика diff (дымовой тест CI без ключа).
- `--verify-review` — pure-проверка парсинга diff/JSON без сети и БД.
- Подключение **чужого** проекта: `integration/` (скопировать `review.yml` + `post_review.py`, задать 3 секрета + `REVIEW_PROJECT`) — см. `integration/README.md`. Движок один на VPS (`server` модуль, `POST /review`), в целевом проекте нет ни Kotlin, ни сборки.
- VPS перед каждым ревью best-effort подтягивает доки (`git pull` + доиндексация, `refresh`), неудача — строка в `warning`.
- Промпт: `buildReviewSystem/buildReviewUser` в `core/src/rag/Prompts.kt` — строгий JSON без фенсов.
- Деплой: `DEPLOY.md` + `Dockerfile.review-server`.

## Task 3 — Ассистент поддержки (День 33)

CRM = **GitHub Issues продукта** (лейбл `support` + `status:*`). Ночной workflow выгружает
тикеты на VPS, сервер разбирает front-matter, раскладывает их в CRM и кладёт в **тот же
RAG-индекс**, что и FAQ — поэтому «такая же ошибка была у других» находится по описанию,
а не только по номеру.

Продукт для демо — [CallowFellow](https://github.com/vladislav-chetrari/CallowFellow):
FAQ в `support/faq.md`, тикеты — Issues с профилем пользователя во front-matter.

### Поток одного сообщения

```
Пользователь (браузер) ──▶ GET /chat                страница чата, без токенов
                        └─▶ POST /support/chat      «модель падает на 80%»
                              ├─ найти обращение в CRM по тексту вопроса (вектор + общее слово)
                              ├─ RAG → FAQ + docs проекта (top-K, цитаты [N])
                              └─ DeepSeek → ответ: признать проблему, опереться на обращение, дать шаг
```

**Пользователь не знает номер обращения** — он просто пишет вопрос. Ассистент сам находит
подходящее обращение в CRM: семантический поиск по корпусу тикетов (тот же RAG-индекс)
плюс проверка, что в вопросе и в обращении есть общее содержательное слово. «А сроки
какие-нибудь известны?» — продолжение разговора, обращение берётся из памяти диалога.

`chatId` в диалоге — идентификатор сессии (нужен, чтобы помнить переписку), а не номер
тикета. История — в `support_chats.json`.

**Про MCP честно.** CRM реализована как MCP-сервер: те же тулы, что отдаёт
`POST /mcp` (`initialize` / `tools/list` / `tools/call`, JSON-RPC 2.0), лежат в
`CrmTools.registry()`. Сам бот на VPS зовёт их **в процессе** — через HTTP-сам-себя
он бы занимал вторую нить пула и рисковал исчерпать его. Наружу MCP открыт как обычный
сервер: `cli mcp-tools --server https://<vps>` делает `initialize` + `tools/list` и
печатает список тулов — это видно, что слой настоящий, а не имитация.

### Ключевые решения

- **Тикет авторитетнее FAQ.** Статус, ответственный, срок и обходной путь берутся только
  из CRM. Если срока в тикете нет — бот обязан сказать «ориентира по срокам пока нет».
- **Что говорить по статусу, считает код, а не модель** (`ticketGuidance`): мелкие LLM путают
  `resolved` и `in-progress`. Поведение воспроизводимо и не зависит от настроек модели.
- **Запрет выдумок** — правила 7–9 в `buildSupportSystem` + отрицательный пример («настройки →
  Система → Диагностика») и потолок `max_tokens = 500`: на длинных ответах модель
  расписывает несуществующие пути и срывается на другой язык.
- **Порядок блоков промпта и бюджет на каждый** (`buildSupportUser`): общий лимит раньше
  резал промпт с конца, из-за чего выпадал именно FAQ — модель отвечала, не видя цитат.
- **Деградация без эмбеддингов**: если Ollama недоступна, ассистент отвечает по тикету из CRM
  и честно пишет об этом в `warning`, вместо того чтобы молчать или упасть.
- **Ночная выгрузка не затирает ручные правки**: снимок GitHub — в `crm/<project>.json`,
  локальные изменения (статус, комментарий, эскалация) — в `crm/<project>.overrides.json`.
- **Обращение ищется по смыслу, а не по совпадению слов**: «экран гаснет» и «обрыв загрузки
  модели» для эмбеддинга похожи (0.64), но это разные проблемы — поэтому кроме score
  требуется общее содержательное слово из текста обращения.

### Команды

```sh
support-ask   --chat s1 --message "текст" [--project CallowFellow] [--server URL] [--topK 8]
support-ticket --list | --id 3 [--status in-progress] [--assignee ilya] [--comment "..."] [--escalate "..."]
mcp-tools     [--server URL]                      # tools/list CRM-сервера по MCP
support-eval  --cases support/cases.json          # 8 кейсов: тикет/статус/фразы/запрещённое
verify-support                                   # оффлайн-проверка слоя, без сети и БД
```

`--server` (или `$VPS_URL`) — работа по сети на VPS; без него тот же код исполняется локально.
Ключ LLM — из `DEEPSEEK_API_KEY` в env (на VPS прилетает в `X-LLM-Key`).

### Эндпоинты

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/chat` | страница чата (без токенов) |
| POST | `/support/chat` | сообщение из браузера → `SupportReply` (без токенов) |
| POST | `/support/ask` | то же для CLI/интеграций (с авторизацией) |
| POST | `/mcp` | CRM как MCP-сервер (JSON-RPC 2.0: `initialize`, `tools/list`, `tools/call`) |
| POST | `/crm/import` | выгрузка тикетов из Issues + индексация их в RAG |
| POST | `/crm/tickets` | текущее состояние CRM |
| POST | `/crm/ticket` | правка тикета: статус, ответственный, комментарий, эскалация |

MCP-тулы: `get_ticket`, `list_open_tickets`, `search_tickets`, `get_user_tickets`.
Номера тикетов в демо — 3…8 (Issues репозитория CallowFellow).

## Task 4 — Ассистент для работы с файлами (День 34)

Агент, который сам инициирует работу с файлами проекта: человек ставит **цель**,
агент сам выбирает файлы, читает, ищет, правит и создаёт. Каждая запись проходит
подтверждение с готовым diff, любой прогон можно посмотреть и откатить.

Работа агента живёт в **отдельных агентных чатах**: в сайдбаре две секции — «Чаты»
(вопросы по базе знаний, RAG) и «🎯 Агентные чаты» (только работа с файлами).
Раньше панель агента висела поверх переписки с вопросами, а история прогонов была
общей на всех, поэтому «что этот чат уже делал» прочитать было нельзя. Теперь у
чата есть вид (`kind`: `RAG` | `AGENT`, Week6/core/src/rag/ChatStore.kt), у агентного
чата — своя история прогонов (`AgentRun.chatId`), а в информационном чате панели
агента нет вовсе.

Запуск — в том же приложении (`./kotlin run --module desktop`) или headless через CLI.
Данные прогона — `~/.ai-advent-week6/agent_runs.json`, снапшоты — рядом, в `agent_snapshots/`.

### Команды

В агентном чате цель ставится полем над панелью агента и кнопкой «▶ Старт»
(в переписке он недоступен: агентному чату не нужны вопросы по базе знаний).
Те же команды работают в CLI и в переписке информационного чата:

```
/goal <цель>      запустить агента (цель, а не файл — файлы выберет он)
/runs             список прогонов
/run-diff [id]    что изменил прогон (unified diff)
/revert [id]      откатить прогон по снапшотам
/autopilot        писать файлы без подтверждения (по умолчанию выкл)
```

Тот же агент доступен headless:

```sh
week6 agent-run --goal "<цель>" [--project P] [--chat <имя>] [--auto-approve] [--max-steps 16] [--out run.json]
week6 agent-tools [--project P]     # схемы тулов: ровно то, что видит модель и MCP-клиент
week6 agent-runs | agent-diff --run <id> | agent-revert --run <id>
week6 verify-agent                  # оффлайн-проверка слоя без сети, БД и LLM
```

`--chat <имя>` привязывает headless-прогон к агентному чату: он появляется в его
истории вместе с diff и доступен для отката из desktop.

### Тулы

Чтение — без вопроса: `list_files`, `read_file` (с диапазоном строк), `grep`
(подстрока или регулярка по всем файлам), `find_references` (объявления + использования),
`git_diff`.
Запись — всегда через подтверждение: `write_file`, `edit_file` (точечная замена
`old_string` → `new_string`, как в opencode). Плюс терминальный `finish`.

Один реестр на два транспорта: те же описания уходят модели в `tools` и в MCP-сервер
(`tools/list` + `tools/call`), поэтому слой не имитируется — `agent-tools` печатает
ровно то, что видит модель. На VPS файловые тулы отдаются по `POST /mcp/agent`
**только на чтение**: по HTTP спрашивать подтверждение некого, а «записывать молча»
нельзя. Запись остаётся там, где есть человек.

### Конечный автомат

`core/src/agent/AgentState.kt` — каталог событий и **чистый редьюсер**
`(state, event) -> {state, commands}`. `sealed interface` + `when` без `else` дают то же,
что в opencode `Match.discriminatorsExhaustive`: новое событие без перехода — ошибка
сборки. Библиотеки конечных автоматов нет, как и в opencode.

Состояния вызова: `Pending → Running → Done | Failed`. Состояния прогона:
`Idle → Goal → Thinking → AwaitingApproval → Applying → Done | Failed | Cancelled`.

Четыре решения, взятые у opencode v2 дословно:

- **Терминальное событие принимается только из нетерминального состояния** — иначе
  повторный replay события перетирает уже записанный результат.
- **Отказ по разрешению обрывает прогон и не возвращается модели текстом** — иначе
  модель по кругу повторяет тот же запрещённый вызов.
- **Продолжение цикла = был локально исполненный тул**; на лимите тулы
  выключаются (`toolChoice = "none"`), и прогон закрывается честным объяснением,
  а не молчанием.
- **Diff считается ДО запроса разрешения** и уходит в диалог подтверждения:
  пользователь решает по сути правки, а не по слову «обновлю документацию».

Границы: только корень проекта (`canonicalPath`, `..` и абсолютные пути отклоняются),
служебные папки (`.git`, `build`, `node_modules`) недоступны, лимиты на шаги (16),
вызовы тулов (40) и изменённые файлы (10) — каждый прогон умеет объяснить,
почему он остановился.

### Воспроизводимость и откат

Прогон — это не «ответ в чате», а запись: цель, шаги, все вызовы с аргументами,
итоговый diff и список изменённых файлов (`agent_runs.json`), плюс `chatId` — какому
агентному чату прогон принадлежит. Перед первой записью файла снимается снапшот;
`/revert` возвращает состояние на момент снапшота.
Файл удаляется при откате **только** если снапшот явно помечен «создан прогоном»:
отсутствующий снапшот никогда не имеет права снести живой файл.
Удаление агентного чата не стирает прогоны — он их только отвязывает (`chatId = ""`),
иначе история работы агента исчезала бы вместе с пустым списком чатов.

### Модели без native function-calling

Локальная `qwen2.5-coder` на Ollama и часть прокси возвращают вызов тула обычным
текстом, а не в поле `tool_calls`. Такой ответ разбирается нами (`ToolCalls.kt`):
принимаются плоская форма (`{"name", "arguments"}`), форма OpenAI
(`{"function": {...}}`), массив и несколько объектов подряд. Если разобрать нечего —
текст уходит пользователю как обычный ответ. Ошибочный вызов (битые аргументы,
неизвестный тул) получает в переписку текст ошибки и **не крутит цикл**.

### Сценарии (проверены на Waifu-KMP, локальная qwen2.5-coder:32b)

1. **Найти все места использования** — `find_references` → 5 × `read_file` → `finish`.
2. **Обновить документацию по коду** — прочитал `NetworkConfig`, `WaifuNetworkConfig`,
   DI и README, затем `edit_file` README с точной заменой; diff приложен.
3. **Сгенерировать новый файл (ADR)** — прочитал 3 файла, создал
   `docs/adr/0001-network-config.md`; откат удалил его и вернул дерево в исходное.

### Проверка

`week6 verify-agent` — 16 групп оффлайн-проверок без сети, БД и LLM: схемы тулов,
разбор аргументов (включая битый JSON), клетка путей, чтение и поиск, unified diff,
plan/apply (diff до записи), снапшоты и откат, разбор вызовов из текста, переходы
редьюсера и гарг терминальных событий, обрыв прогона при отказе, бюджет шагов,
правила разрешений, промпты, MCP-слой, обязательные аргументы и разделение чатов
(вид чата, история прогонов по чату, отвязка при удалении чата).
